You can think of **GitHub** as a Google Drive for its purpose, which is to sync and back up files to the cloud and/or allow collaboration with others. A **repo**, short for repository, is a self-contained project folder with its own permissions, rules, collaborators, and so on. When you **clone** a repo, it makes a local copy of the folder on your system, more like a personal OneDrive than the typical Google Drive setup that lives entirely online.

But crucially, *Git only syncs when you tell it to*. The folder lives as a local copy on your system whose changes you must intentionally **pull** to get the most recent version of the files as stored online, and when you are ready to **commit** your changes, you must **push** them in order to make them available online for other people to sync from. This can cause issues called **merge conflicts** where two people are working on the same file simultaneously and their changes would contradict each other, which makes it important to stay synced.

So why do we use Git if it seems to just be a less convenient version of Dropbox? It's because that intentional syncing makes collaborating on code *safe*.

Imagine everyone working simultaneously on an auto-syncing version of our codebase. If you're an artist who wants to add a new sprite into the game code and see how it looks when you're running the game, but a writer or coder was in the middle of adding dialogue and `"hasn't closed out the quotes on their senten`—then as soon as the artist tries to run the code, it will break with Python script errors for issues in a file they weren't even working on. They will have to wait for the writer to finish writing before they can test their changes.

Git allows for different versioning of the code maintained through **branches**. In a proper repository, the code committed to the **main** branch will be a stable, release-ready version of the code. New additions to the code can be committed to its own individual branch while you're building out; for instance, you could make one called **tiger** for work concerning the tiger shrimp date path. Once you're done with your additions, that branch can **merge** up to the **develop** branch for cohesive testing, alongside all other new features that other folks were working on in parallel. Then once that **develop** version is cleared for release by our intrepid editors and playtesters, we merge it up to **main**.
